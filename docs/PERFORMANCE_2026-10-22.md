# UserInfo v0.1.7 — گزارش عملکرد و حفظ داده

مبنای کار: `caddd2d2f7cb2d0d398f66bdb3de5cac6babfae1`، نسخه 0.1.6.
نتایج این سند از داده کاملاً مصنوعی در Linux و GitHub Actions هستند. هیچ تستی روی POCO X7 Pro یا دیتابیس واقعی کاربر انجام نشده است. پشتیبانی عملی ۱۰۰ میلیون رکورد هنوز تأیید نشده است.

## گلوگاه‌های تأییدشده

- تا پایان FTS، مسیر قبلی نام از `LIKE '%word%'` استفاده می‌کرد و کل جدول را اسکن می‌کرد.
- `LIKE` موبایل با B-tree دارای Collation پیش‌فرض هم‌خوان نبود؛ EXPLAIN اسکن records را نشان داد.
- COUNT پس از هر جستجو و هنگام refresh ایمپورت، صف اتصال SQLite را مشغول می‌کرد.
- OFFSET هزینه‌ای متناسب با عمق صفحه داشت.
- Backfill نام‌ها را به Dart منتقل می‌کرد و برای هر رکورد عملیات Batch جدا می‌ساخت.
- Parser برای هر ردیف یک رویداد async می‌فرستاد. درج هم برای هر ردیف یک عملیات SQLite جدا در Batch داشت.

## نتایج قبل و بعد

### درج واقعی از طریق sqflite FFI، جدول و تنظیمات یکسان

GitHub Actions / Linux / SQLite با journal=delete و synchronous=FULL. هر حالت حدود ۱۰۰ هزار ردیف مصنوعی. داده‌های خام در `performance/host-insert-parser.json`.

| Batch | قبلی، رکورد/ثانیه | درج گروهی، رکورد/ثانیه | P95 قبلی / جدید، میلی‌ثانیه |
|---|---:|---:|---:|
| ۱۰۰۰ | ۹٬۸۸۱ | ۴۵٬۲۱۳ | ۱۰۳٫۶ / ۲۰٫۴ |
| ۱۵۰۰ | ۹٬۹۶۵ | ۴۷٬۱۳۲ | ۱۵۱٫۸ / ۳۰٫۴ |
| ۲۰۰۰ | ۱۰٬۰۳۰ | ۴۸٬۶۱۶ | ۲۰۲٫۲ / ۳۸٫۷ |
| ۵۰۰۰ | ۹٬۹۸۸ | ۴۸٬۳۷۴ | ۴۹۶٫۲ / ۹۸٫۹ |

Batch پیش‌فرض ۱۵۰۰ حفظ شد: افزایش به ۲۰۰۰ سود کمی دارد و زمان هر تراکنش بیشتر می‌شود. این آزمایش هزینه Channel اندروید، SAF و Flash گوشی را اندازه نمی‌گیرد.

### Parser

یک میلیون ردیف، پنج تکرار: میانه قبلی ۳٫۹۸۱ ثانیه، جدید ۳٫۳۹۵ ثانیه؛ نرخ ۲۵۱٬۱۹۳ → ۲۹۴٬۵۲۲ ردیف/ثانیه. Peak RSS فرآیند ۲۰۳٫۷ → ۲۰۵٫۲ MB بود؛ چون در یک فرآیند اجرا شده‌اند این اعداد اندازه مستقل حافظه هر روش نیستند.

### جستجوی SQL، داده مصنوعی

اعداد P50 گرم، میلی‌ثانیه؛ ۹ تکرار. P95 و پلن‌ها در JSONهای `performance/host-query-*` ثبت شده‌اند. اسکیمای آزمایش کوچک‌تر از رکورد بانکی کامل است؛ اعداد آن را به گوشی تعمیم ندهید.

| سناریو | ۱M قبلی → جدید | ۵M قبلی → جدید | ۱۰M قبلی → جدید |
|---|---:|---:|---:|
| نام ناموجود، LIKE → FTS | ۹۹٫۸۰ → ۱٫۰۶ | ۴۷۲٫۰۶ → ۵٫۶۲ | ۹۱۹٫۴۸ → ۱۱٫۳۲ |
| موبایل محدود، LIKE → Range B-tree | ۵۹٫۹۰ → ۰٫۰۰۴ | ۲۷۲٫۳۸ → ۰٫۰۰۴ | ۵۳۱٫۹۰ → ۰٫۰۰۴ |
| صفحه بسیار عمیق، OFFSET → Cursor | ۱۹٫۹۴ → ۰٫۰۱۰ | ۹۷٫۳۷ → ۰٫۰۱۰ | ۱۸۰٫۷۹ → ۰٫۰۱۰ |

مسیر جدول مشتق شناسه‌ها در آزمایش ۱۰M نیز اجرا شد: P50=۰٫۰۰۴ و P95=۰٫۲۱۰ ms. جدول آزمایش اصلی در حالت‌های ۱۰۰K/۱M/۵M فقط مسیر Range روی ستون اصلی را مقایسه می‌کند؛ آزمایش ۱۰M مسیر نهایی جدول مشتق را هم دارد.

## اندازه و انتخاب موتور

در آزمایش ساده ۱۰M، حجم قبل از جدول مشتق شناسه‌ها ۱٬۵۹۰٬۶۷۷٬۵۰۴ و پس از آن ۲٬۴۵۵٬۰۴۸٬۱۹۲ بایت شد؛ افزایش حدود ۸۶٫۴ بایت به ازای هر رکورد برای جدول و دو ایندکس جدید. این هزینه برای پشتیبانی از ارقام فارسی/عربی/انگلیسی مخلوط، بدون تغییر مقدار اصلی شناسه‌هاست. در ۱۰۰M همین مؤلفه به‌تنهایی می‌تواند حدود ۸٫۶ GB اضافه کند؛ کل دیتابیس به طول نام، آدرس و سایر فیلدها وابسته است. ایندکس‌های قدیمی حذف نشده‌اند.

مقایسه ۱۰۰K نام مصنوعی (`host-engine-matrix.json`): FTS4 حدود ۵٫۸۹ MB، FTS5 حدود ۵٫۶۸ MB، جدول Token حدود ۱۲٫۹۱ MB. B-tree نام کامل، کلمه غیرابتدایی را پیدا نکرد. آزمایش Token فقط یک کلمه است و جایگزینی کامل AND چندکلمه‌ای را اثبات نمی‌کند. FTS5 روی میزبان موجود بود؛ وجود آن روی SQLite سیستم POCO تأیید نشده است. بنابراین Hybrid FTS4 + B-tree حفظ شد.

WAL/FULL، WAL/NORMAL، Batchهای ۱۰۰۰/۲۰۰۰/۵۰۰۰، cache، temp_store و mmap روی میزبان مقایسه شدند. نتایج برای انتخاب تنظیم گوشی کافی نیستند؛ تنظیمات پیش‌فرض دستگاه تغییر نکردند. `synchronous=OFF` و `journal_mode=OFF` استفاده نشده‌اند. NORMAL انتخاب نشد؛ تضمین دوام Commit هنگام قطع برق نباید ضعیف شود.

## صحت جستجو

- نام: AND مستقل از ترتیب کلمات، با پیشوند هر کلمه. «حسی» به «حسینی» می‌رسد؛ «سینی» تضمین نمی‌شود. FTS4 جستجوی عمومی وسط کلمه نیست.
- شناسه‌ها: رشته باقی می‌مانند؛ صفر ابتدایی و مقدار اصلی حفظ می‌شود. جدول مشتق، ارقام را برای جستجو یکسان می‌کند.
- تا تکمیل Backfill، نتیجه فقط شامل رکوردهای ایندکس‌شده است؛ UI این محدودیت را اعلام می‌کند. Full Scan پنهان جایگزین نمی‌شود.
- پیشوندهای بسیار عمومی، فیلترهای ترکیبی کم‌گزینش و COUNT دقیق هنوز می‌توانند پرهزینه باشند. فیلترهای پیشرفته پدر/شهر/آدرس الزاماً ایندکس ندارند.
- Cursor از id نزولی استفاده می‌کند. با اضافه‌شدن رکورد جدید در صفحه اول، جابه‌جایی صفحه‌های بعد OFFSET نمی‌خورد؛ Snapshot سراسری میان ویرایش‌ها تضمین نشده است.

## Migration و بازیابی

هیچ DROP/DELETE روی records در Migration اضافه نشده است. نسخه ۶ جدول کوچک مشتق و Triggerها را می‌سازد؛ داده‌های آن در Chunkهای محدود ساخته می‌شوند. FTS موجود حفظ می‌شود و نام‌های از قبل ایندکس‌شده دوباره نوشته نمی‌شوند. Cursor و هر Chunk در یک تراکنش‌اند. نسخه ۷ جدول Checkpoint خالی اضافه می‌کند.

تست‌ها از دیتابیس مصنوعی سازگار با نسخه ۵ استفاده می‌کنند، نه دیتابیس واقعی پنج‌میلیونی. تست قطع Bulk Import، بازکردن دوباره، ادامه Cursor، به‌روزرسانی نام و شناسه، عدم تکرار و سلامت SQLite وجود دارد. تست ImportController شامل ۳۱۰۰ ردیف معتبر، ردیف خراب و فیلد چندخطی است؛ بعد از قطع، ۱۵۰۰ رکورد باقی می‌ماند و ادامه به ۳۱۰۰ می‌رسد. انتخاب دوباره فایل کامل رکوردی اضافه نمی‌کند.

Resume با SHA-256 کل محتوای فایل و شماره منطقی رکورد انجام می‌شود. ثبت رکوردها، imported_count و Checkpoint اتمیک است. برای ادامه، فایل از ابتدا Parse می‌شود و رکوردهای Commit‌شده رد می‌شوند؛ Seek مستقیم بایتی پیاده نشده است. فایل باید در حین دو مرحله خواندن تغییر نکند. این روش هزینه یک خواندن کامل اضافی دارد، اما نام فایل/URI را ذخیره نمی‌کند و تغییر نام فایل مانع شناسایی محتوای یکسان نیست. فایل تغییرکرده یا هم‌پوشان، فایل جدید محسوب می‌شود؛ این قابلیت Dedup هویت اشخاص نیست.

فایل‌های واردشده با نسخه قدیمی فاقد اثر انگشت‌اند؛ اتصال خودکار آن‌ها به CSV جدید ممکن نیست. داده‌های قبلی حفظ می‌شوند و قبل از ورود فایل جدید، هشدار صریح نمایش داده می‌شود. آن فایل‌ها را دوباره ایمپورت نکنید.

برآورد فضای ایندکس UI اولیه و غیرقطعی است (۲۵۶ بایت به ازای فاصله شناسه‌ها). قبل و حین Backfill/Import فضای آزاد کنترل می‌شود و زیر ۶۴ MB عملیات متوقف می‌شود؛ این رزرو تضمین نمی‌کند که تراکنش بعدی همیشه جا دارد. خطای SQLite تراکنش جاری را Rollback می‌کند و Commitهای قبلی باقی می‌مانند.

## محدودیت‌های تحویل و امنیت

- افزایش سرعت درج و Parser روی میزبان اثبات شده؛ افزایش کل مسیر روی POCO، مصرف باتری، گرما، throttling و cold-cache هنوز اندازه‌گیری نشده‌اند.
- Native Import یا Isolate دائمی اضافه نشده: شواهد دستگاه برای پذیرش پیچیدگی و خطر موتور دوم موجود نیست.
- تست‌های خودکار جای تست دستی همه جریان‌های UI روی Android را نمی‌گیرند.
- SQLite و نام‌های نرمال‌شده رمزگذاری نشده‌اند. قفل استاتیک، حفاظت فایل دیتابیس نیست.
- نسخه 0.1.6 با امضای temporary-debug منتشر شده است. اگر نصب روی نسخه قبلی به دلیل امضا رد شد، برنامه قبلی را بدون بکاپ حذف نکنید. ابتدا از داخل همان نسخه خروجی SQLite بگیرید و وجود فایل را بررسی کنید. پیکربندی امضای ثابت با Secretهای موجود Workflow راه‌حل آپدیت‌های آینده است؛ کلید خصوصی نسخه قبلی در دسترس این مأموریت نیست.
