# UserInfo — انتقال دیتابیس به گوشی دیگر و امضای ثابت APK

## محافظ انتشار پس از v0.1.13

**هشدار جدی:** نسخه‌های v0.1.12 و v0.1.13 با امضای
`temporary-debug` منتشر شده‌اند؛ بنابراین نمی‌توان آن‌ها را
به‌عنوان یک زنجیره آپدیت قابل اتکا در نظر گرفت.

GitHub Actions از این به بعد قبل از ساخت APK نسخهٔ اصلی،
انتشار را با خطا متوقف می‌کند مگر اینکه هر چهار Secret امضای ثابت
تنظیم شده باشند. بیلدهای Pull Request برای تست می‌توانند از
امضای موقت استفاده کنند، ولی نسخه قابل نصب روی `main` بدون
امضای دائمی ساخته و منتشر نمی‌شود.

**حتی اولین نسخه با امضای دائمی هم نمی‌تواند روی APK قدیمی
دارای امضای ناسازگار نصب شود.** انتقال یک‌باره فقط بعد از
گرفتن بکاپ سالم و *موفقیت واقعی ریستور روی دستگاه دیگر*
قابل توصیه است. برای کاربران دارای بکاپ با `quick_check`
ناموفق، حذف اپ نصب‌شده خطر از دست رفتن دائمی اطلاعات دارد.

پس از تنظیم Secretها، حتماً امضای اولین APK دائمی را با
`apksigner verify --print-certs <APK_PATH>` ثبت کن و
در نسخه‌های بعدی با همان گواهی مقایسه کن. هرگز keystore
را عوض نکن و از آن در محل امن بکاپ بگیر.

## ۱. چرا آپدیت مستقیم نسخه‌های قدیمی کار نمی‌کند؟

اندروید فقط وقتی آپدیت APK را روی برنامه نصب‌شده قبول می‌کند که:
- شناسه برنامه (`applicationId`) یکسان باشد؛ در UserInfo باید `com.amindada021.userinfo` بماند.
- نسخه جدید `versionCode` بالاتر داشته باشد.
- گواهی امضای APK با برنامه نصب‌شده سازگار باشد.

GitHub Actions فعلی اگر چهار Secret انتشار تنظیم نشده باشند، برای هر اجرا
از امضای موقت/Debug استفاده می‌کند. گواهی امضای این اجراها معمولاً یکی
نیست. هیچ تنظیمی در Flutter یا `pubspec.yaml` نمی‌تواند محدودیت امنیتی
امضا را دور بزند.

**بدون دسترسی به کلید امضای نسخه نصب‌شده، آپدیتِ درجا ممکن نیست.**
این یعنی پس از نصب اولین نسخه با کلید دائمی احتمالاً یک **جابجایی یک‌باره
با بکاپ معتبر** لازم است؛ اما بعد از آن با حفظ کلید امضا، نسخه‌های بعدی
بدون حذف اپ نصب می‌شوند.

## ۲. ساخت کلید امضای دائمی روی Windows

کلید را فقط روی کامپیوتر خودت بساز، نه در ChatGPT، GitHub و هیچ چت یا
ریپازیتوری عمومی. `keytool` همراه JDK/Android Studio نصب می‌شود.

```powershell
New-Item -ItemType Directory -Force "$env:USERPROFILE\UserInfoSigning" | Out-Null
keytool -genkeypair -v -storetype PKCS12 -keyalg RSA -keysize 3072 -validity 10000 -alias userinfo_release -keystore "$env:USERPROFILE\UserInfoSigning\userinfo-release.jks" -dname "CN=UserInfo, OU=Mobile, O=LocalApp, C=US"
```

برای keystore و کلید، گذرواژه **قوی و منحصربه‌فرد** انتخاب کن و در مدیر رمز
یا محلی امن و خارج از پروژه نگه دار. خود فایل `.jks` را هم در حداقل دو
محل امن پشتیبان بگیر؛ گم‌شدن کلید، آپدیت نسخه‌های نصب‌شده را غیرممکن می‌کند.

در مخزن GitHub به `Settings > Secrets and variables > Actions` برو و
چهار Repository Secret بساز:

- `USERINFO_ANDROID_KEYSTORE_B64`: رشته Base64 تمام فایل JKS. آن را در
  PowerShell به صورت محلی در کلیپ‌بورد کپی کن:
  ```powershell
  [Convert]::ToBase64String([IO.File]::ReadAllBytes("$env:USERPROFILE\UserInfoSigning\userinfo-release.jks")) | Set-Clipboard
  ```
  سپس مستقیم در فیلد Secret در GitHub Paste کن و کلیپ‌بورد را پاک کن.
- `USERINFO_ANDROID_KEY_ALIAS`: مقدار `userinfo_release`.
- `USERINFO_ANDROID_KEY_PASSWORD`: رمز کلید (Key Password).
- `USERINFO_ANDROID_STORE_PASSWORD`: رمز keystore (Store Password).

در Releases بعدی، وضعیت `persistent` باید جای `temporary-debug`
نمایش داده شود. این Secretها را قبل از اولین نصب با کلید جدید تنظیم کن
و پس از آن **دیگر کلید امضا را عوض نکن**.

## ۳. بکاپ و ریستور بین دو گوشی

فایل بکاپ `.sqlite` از Android Storage Access Framework گرفته می‌شود
و حاوی تمام رکوردها، علاقه‌مندی‌ها، ویرایش‌ها، تنظیمات و ایندکس‌های ذخیره‌شده
است. نام دستگاه و شماره سریال گوشی در مسیر ذخیره‌سازی دیتابیس قفل نشده‌اند.

۱. در گوشی مبدأ و **پس از پایان ایمپورت و ایندکس‌سازی**، از Settings
بکاپ کامل بگیر و فایل خروجی را جدا نگه دار.
۲. فایل را با کابل/حافظه USB/اشتراک‌گذاری امن به گوشی دوم منتقل کن.
۳. همان UserInfo (با نسخه برابر یا جدیدتر و ساختار دیتابیس سازگار) را
روی گوشی دوم نصب کن.
۴. در Settings گزینه «بازیابی دیتابیس» را بزن؛ فایل را انتخاب کن.
۵. منتظر پایان انتقال و `PRAGMA quick_check` بمان.
۶. بعد از بالا آمدن برنامه، تعداد رکوردها و چند داده **آزمایشی شناخته‌شده**
را بررسی کن. تا پیش از این تأیید، نسخه مبدأ یا بکاپ اصلی را حذف نکن.

بکاپ‌های قدیمی نسخه `v0.1.6` قبل از کپی WAL، checkpoint صریح
نداشتند؛ بنابراین حتی اگر فایل SQLite ظاهراً ۵ گیگ باشد، ممکن است
همه تراکنش‌ها داخل آن وجود نداشته باشند. اگر انتقال نسخه ۱.۶
روی ۱.۷ خطا داد، **علت دقیق را بدون خروجی خطا نمی‌توان تعیین کرد**.
در صورت امکان روی کامپیوتر و فقط به‌صورت محلی بررسی کن:

```powershell
sqlite3.exe "UserInfo-backup.sqlite" "PRAGMA quick_check; PRAGMA user_version; SELECT COUNT(*) FROM records;"
```

هرگز فایل اصلی را تغییر نده و اطلاعات شخصی را در لاگ عمومی نریز.
اگر `quick_check` موفق بود، هنوز لازم است بازیابی روی نسخه جدید با
Migration مناسب امتحان شود.

## ۴. روشن نگه داشتن صفحه در عملیات طولانی

از نسخه `v0.1.10` هنگام Import/Backup/Restore از
`FLAG_KEEP_SCREEN_ON` روی Activity استفاده می‌شود. این پرچم فقط زمانی
که صفحه برنامه در جلو است، خاموش‌شدن خودکار را متوقف می‌کند؛
قفل دستی با Power، بستن برنامه یا انتقال آن به پس‌زمینه همچنان عمل
می‌کنند. بعد از اتمام یا خطا، پرچم در `finally` برداشته می‌شود.

این ویژگی جای Resume قابل اعتماد و مدیریت Background Android را نمی‌گیرد.
